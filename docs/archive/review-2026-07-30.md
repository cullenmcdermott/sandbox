## HIGH VALUE

### [R1] De-serialize the Connect critical path (speed, ~400-700ms/attach)

One coherent refactor, four cuts:

- **[R1a]** `client/session.go:334` `backend.Status` already does Sandbox Get +
  pod List and sets `st.PodReady` (`internal/k8s/backend.go:1481-1483`); then
  every full connect (`client/session.go:382-391`; observer streams skip it)
  calls `StartWithProgress` → `waitForPodReady` (`backend.go:1583`) whose
  first poll repeats the same two calls. Skip the readiness wait when
  `st.PodReady && st.Status == StatusRunning` and the session wasn't just
  created/resumed (`fresh`). Safe against the two traps the wait exists for:
  the stale-node case forces `PodReady=false` in Status itself
  (`backend.go:1473-1480`), and the terminating-old-pod-on-resume trap
  (`backend.go:1593-1601`) only arises on the resume path, which `fresh`
  already excludes from the skip.
- **[R1b]** `getPodForSandbox` (`backend.go:1695-1700`) uses only
  `sb.Name`/`sb.Namespace`, both derivable from `ref` without the preceding
  Sandbox Get — yet `PortForward` (`internal/k8s/portforward.go:50-57`),
  `Exec` (`backend.go:1061-1068`), `PodIP`, `pinRunnerImageDigest`, and every
  1s tick of `waitForPodReady` (`backend.go:1584`) do the Get first,
  serialized. Pass `ref`, List pods directly; keep a Sandbox Get only where
  the object's absence must be distinguished.
- **[R1c]** `pinRunnerImageDigest` (`backend.go:1053`, body ~:1290+) runs
  foreground inside `StartWithProgress` on every full Connect — a
  RetryOnConflict Sandbox Get + pod List even when the annotation already
  matches. Its own comment says it's best-effort and only affects a later
  resume. Background it (detached context) or gate on "annotation absent".
- **[R1d]** `client/session.go:439` fetches the runner bearer token (Secret
  Get) after `PortForward` returns, and `:574` fetches the opencode password
  after health + sync — two serial Gets of the *same* Secret
  (`backend.go:1101`, `:1116`). Kick one Secret Get concurrently with
  `PortForward` (~`session.go:405`, errgroup) and read both keys from it.

### [R2] Pane WS compression is off on both ends (visual, biggest lever)

Reattach replays up to 256KiB (`runner/src/claude-pane.ts:49`) of uncompressed
ANSI as one frame; terminal output compresses 10-20×. `runner/src/server.ts:203`
builds `WebSocketServer({ noServer: true, maxPayload })` — `ws` defaults
`perMessageDeflate: false` — and the Go client dials with
`websocket.DefaultDialer` (`internal/runner/pane.go:101`), `EnableCompression`
also false. Enable both; also raise gorilla's 4KiB Read/WriteBufferSize to
32-64KiB. Directly shortens attach → readable pane. One caveat when enabling:
`ws`'s permessage-deflate has documented memory/fragmentation overhead per
connection — fine here (one pane client per session, [S5] maxPayload already
bounds frames), but set conservative `zlibDeflateOptions`/window bits rather
than accepting the defaults blindly.

### [R3] Codex connect pays a guaranteed +1s (speed, new in the 07-28 diff)

`probeCodexOnce` (`client/sync.go:482-499`) defines *success* as blocking the
full 1s read-deadline hold; `waitCodexReady` (`:452`) passes `hold=1s`, so a
healthy codex session always burns a full second at `session.go:607`. Right
fix: the runner already supervises the child (`runner/src/codex.ts:252`) and
answers authenticated `/healthz`/`/status` over the same forward just
health-checked — expose a `codexReady` field there and drop the TCP
dial-and-hold. Same argument retires `waitOpencodeReady`'s HTTP probe
(`sync.go:410`). Also closes [R16].

### [R4] Pane child spawns at 80×24 before the client's geometry arrives (visual)

`claude-pane.ts:332-333` defaults cols/rows 80×24; `attach()` (`:374`) calls
`ensureSpawned()` before any client frame can be read (`server.ts:226-229`
attaches inside `handleUpgrade`, registers `ws.on('message')` after), and the
client sends its resize as the first post-handshake frame
(`internal/runner/pane.go:113-117`). Every first attach paints a full 80×24
screen then reflows one RTT later. Fix: carry `?cols=&rows=` on the upgrade
URL (`server.ts:222` already parses `url.searchParams` for `traceId`) and pass
into `pane.attach(adapter, cols, rows)` so the lazy spawn uses real geometry.

### [R5] Reconnect-path sync failures are swallowed (bug, silent data loss)

- `client/session.go:784-788`: the non-`created` (reconnect) path fires
  `_ = mgr.FlushAll(fctx, id)` in a detached goroutine and drops the error —
  no warning, no syncTask contribution — while the `created` path (`:750-778`)
  classifies flush failure via `StatusSummary`. Detaching the flush is
  deliberate and fine (the comment at `:780-783` is right that a healthy
  mutagen session reconciles on its own); the gap is that when the flush
  FAILS nothing ever consults `StatusSummary`, so a mutagen transport that
  died across suspend/resume reconnects "clean" and edits silently stop
  propagating. `SyncForwardAlive()` (`session.go:246`) can't see it because
  the SSH forward is healthy. Keep the flush detached, but on error run the
  same `StatusSummary` classification and surface an advisory (via the
  syncTask/AwaitSync path or a session warning callback).
- `client/sync.go:313`: `_ = mgr.ResumeAll(ctx, id)` — the comment above it
  explains that a failed un-pause leaves "files frozen with no error", then
  discards exactly that error. Propagate into `syncWarning`.

## Second tier

### [R6] Fixed 1s readiness poll intervals (speed)

`waitHealthyWithin` (`client/sync.go:383-403`), `waitOpencodeReady` (`:410`),
`waitCodexReadyWithin` (`:459`) all sleep a flat 1s between probes that ride an
established loopback forward and cost microseconds — average ~500ms dead tail
on resume. Start ~100ms, back off to 1s (same reasoning as
`waitForPodReady`'s "2s → 1s" comment, `backend.go:1579`).

### [R7] Four serialized mutagen CLI spawns in the connect foreground (speed)

`session.go:533` `sameDirSyncWarning` → unfiltered `mutagen sync list`; then
`:547` `startProjectSync` → `ResumeAll` + `CreateProject` →
`sessionSyncsByName` (a second, label-scoped list) + maybe `sync create`
(`internal/sync/sync.go:284-315`, `:276-292`, `:484`). In value order: (a) fold
`startProjectSync` into `startBackgroundSync`'s goroutine (nothing foreground
consumes `created` except flush gating, already backgrounded); (b) one
unfiltered List feeding both the collision warning and the existence map;
(c) skip `sameDirSyncWarning` on reconnect when the project sync exists.
Note the code comment at `session.go:531` calls this List "off the hot path" —
it is off the per-turn path but squarely on the connect foreground; correct
the comment when touching this.

### [R8] `waitForPodReady` polls where an informer already exists (speed)

`backend.go:1583` polls at 1s × 2 API calls per tick (60 RTs over a 30s cold
start) while `internal/k8s/watch.go:87` already runs a Sandbox informer with
readiness from conditions (`sandboxReady`, `watch.go:273`). Drive the wait off
the watch; fall back to polling if the informer can't start. CAVEAT: the
Sandbox informer carries no pod-level detail, so the `onPhase` splash text
("scheduling" / "pulling image" / "starting", `podPhaseDetail`) would coarsen
unless a pod informer supplements it — decide whether that granularity is
worth keeping before doing this one.

### [R9] No resize coalescing anywhere on the pane path (visual)

`internal/tui/dashboard/external_pane.go:710-729` enqueues a control frame per
`WindowSizeMsg`; `server.ts:236` applies each straight to `pane.resize` →
ioctl + SIGWINCH (`claude-pane.ts:423-429`). An edge drag = a redraw storm,
each full-screen repaint crossing the 60ms link. Trailing debounce (~40-60ms)
on the runner side of `resize()` — the source end, which also interacts
correctly with [R10].

### [R10] The 80ms repaint hold races the client's initial resize (visual, new in the 07-28 diff)

`claude-pane.ts:404-411`: `AttachPane` sends its initial resize ~1 RTT after
handshake (`pane.go:113`) — inside the 80ms window — and `resize()` applies
the restored geometry early, shrinking the effective hold toward `min(80ms,
RTT)` and re-exposing the SIGWINCH-coalescing no-repaint bug on fast links
(local forward, or after [R4]). The timer handle also isn't retained, so a
rapid re-attach can schedule a second restore firing against the first jiggle.
Fix: retain + `clearTimeout` in `attach()`/`stop()`; suppress a same-size
client resize while a repaint is pending.

### [R11] Codex readiness wait emits no OnPhase stage (UX, new in the 07-28 diff)

`client/session.go:599-617` runs `waitCodexReady` (≥1s, up to 30s) with no
`stage(...)` — the splash freezes on "sync" for the whole wait, unlike the
opencode branch (`stage(StageOpencode)`, `:585`). Reuse `StageOpencode` or add
`StageExternal`; also update `Stage`'s doc comment (`session.go:29`).

### [R12] `probeCodexOnce` half-opens a real connection per retry (robustness, new in the 07-28 diff)

`client/sync.go:482-499` bare-TCP dials the app-server's WS listener, holds
1s, closes with no upgrade — up to 30× on a slow start. The server allocates a
connection and sees an abrupt close each time; harmless today, noisy under a
stricter/rate-limiting app-server. [R3]'s runner-side readiness field removes
the class.

## Codex cross-check (GPT-5.6 Sol, same day)

An independent Codex consult over the same files corroborated [R1d] (token
prefetch), [R3] (the 1s hold — it additionally argues the dial-and-hold can
*false-pass* while the pod-side dial is still pending, and proposes a real WS
Upgrade requiring `101 Switching Protocols` as a probe that validates the
endpoint without speaking JSON-RPC — a fallback if the runner-side readiness
field is unwanted), [R4] (geometry in the attach handshake), [R5]
(`ResumeAll` — adding that a paused pre-existing sync makes `CreateProject`
succeed as a no-op, attaching the agent to a stale workspace), and [R7]
(`sameDirSyncWarning`). Net-new findings:

### [X1] Reaper ensure is serialized behind the initial flush (cost exposure, not attach latency)

`client/session.go:743-805` — inside `startBackgroundSync`'s goroutine (so
this never delays the attach itself), reaper ensure (`:802-808`) runs after
the flush block and `CreateInputs`. On the first-connect (`created`) path
that's up to the full 12s flush budget + input-sync creation before idle-cost
protection exists; on reconnect the flush is already detached, so only
`CreateInputs` gates it. Run reaper ensure concurrently within the background
task; merge warnings at completion.

### [X2] Post-forward steps are independent but serial (speed)

`client/session.go:457-563,573-617` — runner health, external-service
readiness (opencode/codex), and project-sync setup are independent once the
forwards exist but run serially. Start concurrently, join required results.
(Superset of [R1]'s spirit applied to the post-forward half; codex's wait sits
at the end of the chain today, stacking its second on top of everything else.)

### [X3] Scrollback replay can start mid-ANSI-sequence (visual)

`claude-pane.ts:133-155,350-385` — the ring is a byte-trimmed tail, so replay
can begin mid-escape-sequence and paint garbage at stale dimensions until the
forced repaint. With [R4]'s geometry-first attach in place, the residual fix
is replaying from a safe reset/full-frame boundary (or a terminal-state
snapshot instead of a byte ring).

### [X4] Stale repaint timer can hit a respawned PTY (bug)

`claude-pane.ts:404-410,498-515` — the 80ms restore callback dereferences
whatever `this.pty` exists when it fires; if the child exits and respawns
inside the window, an old timer resizes the *new* PTY. Same remediation
cluster as [R10]: retain the timer id, cancel on exit/stop/attach, and tie the
restore to the PTY instance it jiggled.
